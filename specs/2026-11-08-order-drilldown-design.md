# Order drill-down (detail pages) — design

Date: 2026-11-08
Status: draft, awaiting review

## Goal
Let a viewer click a row in the `Latest orders` table and open a detail page showing the order and, in a
separate card, the customer who placed it. Done to learn the drill-down pattern on the existing static,
config-driven architecture (no server).

## Decisions (agreed with the user)
- Click origin: the `Latest orders` table only (not the trend chart).
- Approach A: per-record JSON files + one generic `docs/detail.html`.
- Stay on the demo SQLite DB; add a `customers` table with fake data.
- Feature is opt-in per metric via config; metrics without `detail` behave exactly as before.

## Constraints
- Static GitHub Pages: the browser cannot query the DB, so all detail data is pre-generated by `poll.py`.
- Public repo/Pages: customer PII must not be published for real data (see Privacy).
- No new dependencies beyond pyyaml (project rule). Tests use the standard library only.
- DB access stays read-only; DB error text never goes into public JSON.

## Data model (demo)
- New table `customers(id, name, email, country, segment)`, ~40 fake customers.
- `orders` gains `customer_id` (references `customers.id`).
- `demo_db.py` creates both and assigns each order a random customer. The demo DB is regenerated on every
  workflow run, so no migration is needed; locally delete `demo.sqlite` once.

## Config contract (`config.yml`)
Optional `detail` block on a metric:
```yaml
detail:
  key: id                  # column of the metric result used as the record key
  title: "Order {id}"      # {column} placeholders filled from the metric row
  sections:                # each SQL returns one row -> one card
    - title: Order
      sql: SELECT ... FROM orders WHERE id = ?
    - title: Customer
      sql: SELECT ... FROM customers WHERE id = (SELECT customer_id FROM orders WHERE id = ?)
```
`?` is replaced by the key value; `poll.py` rewrites it to `%s` for postgres. Every `?` in a section
SQL receives the same key (parameters are passed positionally, one per `?`).

## `poll.py` behaviour
1. Run the metric query as today.
2. If the metric has `detail`: for each row, take `row[key]`, validate it against `^[A-Za-z0-9_-]+$`
   (skip and warn otherwise; also validate the metric name the same way), run each section SQL with that key.
3. Write `docs/data/details/<metric>/<key>.json`:
   ```json
   {"metric": "latest_orders", "key": "123", "title": "Order 123",
    "sections": [{"title": "Order", "columns": ["a"], "row": [1], "error": null}]}
   ```
   No timestamp inside, so unchanged data produces byte-identical files and no commit noise.
   Write only when content differs.
4. Delete files in `docs/data/details/<metric>/` whose key is no longer in the current result.
5. A failing section sets only that section's `error` to a generic message (details to the Actions log via
   `::warning::`); other sections and metrics continue. The metric's main result is unaffected.
6. Add `"detail": {"key": "<column>"}` to the metric entry in `dashboard.json` so the UI knows it is clickable.

`dashboard.json` contract change: optional `detail: {key}` on a metric. Nothing else changes.

## UI
- `index.html`: for `table` metrics with `detail`, render the key cell as a link to
  `detail.html?metric=<name>&key=<value>` (link built with `encodeURIComponent`; pointer cursor / hover on the row).
- New `docs/detail.html`: same theme tokens and layout as `index.html`; validates `metric` and `key` against
  the same regex, fetches `data/details/<metric>/<key>.json` (`cache: 'no-store'`), renders each section as a
  key/value card, shows a back link to `index.html`. On 404 shows "This record is no longer available
  (it may have dropped out of the table)". Section with `error` shows a badge. All values via `textContent`.
- Light/dark theme and single-column mobile layout as in `index.html`. The small amount of shared CSS is
  duplicated in `detail.html` (single-file pages, no build step).

## Workflow
- Commit step changes from `git add docs/data/dashboard.json` to `git add -A docs/data` so detail files
  (including deletions) are committed.
- Add `docs/detail.html` to the push trigger paths, next to `docs/index.html`.

## Privacy
- Opt-in per metric; demo customers are fake.
- Add to `CLAUDE.md` and `MIGRATION.md` (Phase 3 prerequisite): before pointing `detail` at real data, do not
  publish personal data (names, emails) on public Pages — use anonymised/aggregate fields or access-controlled Pages.

## Testing
`scripts/smoke_test.py` (stdlib `unittest`, runs against a temp dir/DB):
- demo DB → poll → 10 detail files exist, each with 2 sections and no errors.
- Second poll with no new data leaves detail files byte-identical.
- After `demo_db.py --tick 5` + poll, files for keys that left the table are removed.
- A key containing `../` is rejected and writes nothing.
Then a manual browser check with `python -m http.server -d docs 8000`: click a row, see both cards, back link works,
a bogus `key` shows the not-available message.

## Out of scope
Trend-point click-through, pagination, search, charts inside detail pages, details for more than the rows
the metric returns.

## Known trade-offs
- Only rows currently in the table have detail pages; links to older orders break (handled with the message above).
- `detail.html` duplicates some CSS from `index.html`.
